# Cowork device enrollment web boundary

`CoworkDeviceEnrollmentModel` and `CoworkDeviceEnrollmentPanel` are an adoption-ready, web-only presentation boundary over PR #20's audited device-key authority. They have no production wiring. The component renders nothing unless both a client and an exact-device signer are explicitly injected, and it performs no signer or client work until the operator selects **Enroll this device**. The slice creates no timer, storage entry, network connection, RPC, socket, process, provider request, agent task, WebCrypto key, or background subscription.

The caller supplies the authenticated shared project, user, device, and membership epoch. The injected signer may return only that exact public identity and expose `signEnrollmentProof(challenge, nonce)`. There is no private-key export field or callback. The model captures those four exact client/signer methods once, keeps the adapter receivers private, and never publicly re-exports the injected capability objects; later in-place method replacement therefore cannot change authority mid-flow. The panel rejects cross-project, cross-user, cross-device, stale-epoch, excess, accessor-backed, inherited, proxy-wrapped, sparse, symbol-bearing, malformed, noncanonical, identity, and low-order Ed25519 public-key data before enrollment. The browser repeats the server's prime-order compressed-point validation as defense in depth; the server remains authoritative and verifies the proof.

Begin sends one frozen request binding its command identifier, project, and exact signer's public key. A successful challenge must bind the current project, user, device, membership epoch, public key, server challenge/key identifiers, and the fixed five-minute server lifetime. The nonce is never placed in React/display state. It is held only with that challenge in one private in-memory model object, passed directly to the exact-device signer, and then moved into one frozen complete request with the returned proof. Complete must return the exact project/user/device/epoch/key/public-key authority activated inside the challenge interval. The model rechecks lifecycle authority after every observer notification and injected callback, so synchronous stop, scope replacement, or unmount cannot invoke the next capability or reattach a nonce-bearing attempt after cleanup. It clears nonce/proof-bearing references on definitive success, explicit discard, scope replacement, stop, or unmount. JavaScript strings cannot be securely zeroed, so this boundary promises prompt reference removal rather than impossible memory erasure; injected adapters must likewise avoid retaining, serializing, logging, exporting, or diagnosing nonce/proof values beyond the authenticated request they own.

Transport failure is an indeterminate acknowledgement. Begin and complete retries reuse the same frozen request object and command identifier; no retry silently changes project, identity, key, challenge, nonce, or proof. The server intentionally stores only a nonce digest, so an exact replay of an applied begin returns `already-applied` with `nonce: null`. The panel then labels the attempt unrecoverable, never signs, never reconstructs or requests a second nonce, blocks enrollment, and requires explicit discard before a new command may begin a separate challenge. A malformed or scope-drifted complete response also retains only the exact original request for a possible idempotent retry; it never treats an unbound receipt as activated authority.

This child deliberately omits current-key listing and standalone revocation. PR #20 exposes a server store but no authenticated current-key listing surface that could prove which key belongs to the exact current user and device. Inventing client-supplied key metadata or a free-form revocation identifier would create an authorization illusion. Enrollment rotation is supported honestly because the audited server completes it by revoking the prior project/device key and inserting the replacement in one writer transaction. A future listing/revocation child must add a separately audited, project-authorized read contract and require explicit confirmation bound to the exact current user, device, membership epoch, and listed current key.

Production adoption still requires an OS-backed non-exportable private-key implementation, authenticated project-scoped begin/complete RPCs, principal/session renewal, and independent transport and keystore audits. This slice does not claim a WebCrypto persistence strategy, operating-system keystore, coordinator transport, live enrollment endpoint, or deployable device revocation workflow.
